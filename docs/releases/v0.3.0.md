# v0.3.0 - POS, Nuki, attendance and per-user attribution

This stable release promotes the cumulative v0.3.0b1–b4 feature set. Its runtime
behavior is unchanged from v0.3.0b4; this release updates the version and makes
that behavior available to stable HACS installations.

## Included features

- POS resources expose read-only successful authorization events.
- Nuki resources report synchronized lock state and battery level while retaining
  the Fabman access switch.
- Check-in terminals contribute to a space-level attendance roster and emit
  check-in/check-out events. They remain read-only.
- Accepted bridge commands have a bounded confirmation deadline and a persistent
  Home Assistant notification when execution is not confirmed.
- Administrators can map Home Assistant users to Fabman members by numeric ID or
  exact email. Per-resource activation events and status attributes expose the
  Home Assistant actor and attribution outcome.
- Email mappings accept only one exact email match in the integration's Fabman
  account. Numeric member IDs continue to work.

## Member attribution behavior

This release retains the existing post-activation attribution flow. The integration
starts equipment using the configured API account, confirms the bridge command,
matches the new activity-log entry and then reassigns that entry to the selected
member with optimistic locking. It does **not** send the selected member in the
`switch-on` request, so Fabman does not check that member's resource permissions,
training or presence during activation. The API account's permissions authorize
the remote activation. Attribution can affect the selected member's charges.

If Fabman accepts activation but attribution cannot be confirmed, the equipment may
already be on and the log may still belong to the API member. Check Fabman's activity
log before taking further action; do not repeat activation just to retry attribution.
Concurrent controls outside Home Assistant cannot be correlated atomically.

## Other limits

- Check-in roster and latest activation details are held in memory and reset when
  the integration reloads or Home Assistant restarts.
- Bridge command timeouts do not retry activation, switch the resource off or
  cancel a command still queued at Fabman.
- Nuki status can be stale until Fabman refreshes its connection. Nuki command
  behavior and live POS/Nuki telemetry still need a controlled hardware pilot.
- Activity and Connectivity are Fabman-reported states, not physical contact or
  immediate hardware measurements. See the [activity contract](../activity-contract.md).

## Upgrade or rollback in HACS

Install **v0.3.0** from the Fabman entry in HACS and restart Home Assistant. Beta
versions do not need to be enabled. Existing configuration and entity identities
are preserved; no new API token or configuration entry is required.

This release adds POS, Nuki, attendance and activation-event entities. Review
automations that depend on new entities before enabling them. To roll back, select
stable **v0.2.0** in HACS and restart; v0.2.0 lacks the v0.3.0 POS, Nuki, attendance
and HA-user mapping features. Updating or rolling back does not cancel queued
Fabman commands.

## Validation history

The v0.3.0b3 beta notes report 329 passing tests on Home Assistant 2026.10.1 and
2026.10.2 with Ruff checks passing. The stable promotion contains no
integration-code changes beyond v0.3.0b4. Automated live checks of Nuki commands,
POS events and attendance remain part of the controlled pilot; the release does
not claim those hardware behaviors were verified.
