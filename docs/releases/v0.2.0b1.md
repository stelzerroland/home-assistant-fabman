# v0.2.0b1 - Activity sensors and timed door release (beta)

This prerelease adds native binary activity sensors and corrects how uncertain
usage and pending bridge commands are represented. It is intended for passive
comparison before migrating production automations. Stable users can keep v0.1.1.

## Changes

- Each supported Fabman resource gains an `Activity` binary sensor on its existing
  device. Existing sensor/switch identities and webhook URLs are preserved.
- Machine activity requires consistent session data. Missing, ambiguous or
  contradictory usage becomes `unknown`; API failures and missing resources
  become `unavailable`.
- Door release is `on` until `lastUsed.at + maxOfflineUsage`, then `off` locally,
  even without polling or a server off event. Repeated reads do not extend the
  window. A new successful grant establishes a new deadline. This describes the
  electrical release window, not a physical door contact.
- Accepted bridge commands no longer overwrite API usage. Switches expose an
  assumed state; status/activity sensors remain unknown until matching evidence.
  An unchanged previous door grant cannot confirm another opening command.
- Pagination is atomic, including later-page failures. Malformed responses,
  resource IDs, rate limits and overlapping asynchronous reads are handled without
  publishing partial lists or stale state.

## Behavior changes and remaining limitations

Existing status sensors also use the corrected state contract. In particular,
`lastUsed: null` is unknown until never-used semantics are verified. Door durations
that are missing, zero, negative or invalid remain unknown. An API success does
not prove that each bridge is online; offline/freshness semantics still need
verification using real responses.

A pending command can remain assumed until matching usage, another command,
resource removal or reload. Command-completion polling is not included yet.
An `off -> unknown -> on` transition does not trigger an automation requiring
exactly `off -> on`. Include this in pilot comparisons. No production light or
door automations are changed by this release.

Dynamic resource discovery and an options flow are not part of this beta.
New resources require an integration reload.

## Install through HACS

1. Back up the current Home Assistant configuration.
2. Open the Fabman repository in HACS and choose **Redownload**.
3. Choose **Need a different version?** and select `v0.2.0b1`. Depending on your
   HACS version, enable beta/prerelease versions first.
4. Download and restart Home Assistant completely.
5. Check the additional `Activity` entities under Settings > Devices & services >
   Fabman. No new configuration entry or API credentials are required.

For ongoing beta update notifications, enable the repository's prerelease switch
in HACS (the entity can be disabled by default). Regular stable-only installations
continue using the stable release.

To roll back, redownload `v0.1.1` through HACS and restart Home Assistant. This beta
does not migrate stored configuration or change existing entity unique IDs.

## Validation

138 tests pass against both Home Assistant 2026.10.1 and 2026.10.2. Tests use
synthetic API responses and local HTTP servers; no real bridge commands were sent.
The historical HACS minimum of HA 2023.1.0 is unchanged and has not been tested.
See the [activity contract](../activity-contract.md) for the detailed interpretation
and remaining pilot checks.
