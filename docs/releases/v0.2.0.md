# v0.2.0 - Activity, connectivity, resource synchronization and member assignment

This stable release incorporates the cumulative changes from v0.2.0b1–b6.
Runtime behavior is unchanged from b6; the version and documentation now identify
v0.2.0 as stable. The changes and current README are included on main.

## Changes since v0.1.1

- Native **Activity** and **Connectivity** binary sensors on existing Fabman devices.
  Connectivity follows the explicit bridge offline flag. Uncertain activity is
  unknown; failed API reads and inactive/missing resources are unavailable.
- Accepted commands produce an assumed switch state until API observations confirm
  the result. Completed machine usage timestamps are interpreted correctly.
- Door release state expires locally after `maxOfflineUsage`, even without a server
  off event. A confirmed short release clears its pending command even if it has
  already expired when HA reads it. Activity is not a physical door contact.
- New supported active/locked resources are discovered on successful complete
  refreshes. Known archived/deleted/missing resources remain unavailable and can be
  removed locally after a trustworthy inventory read. Source renames preserve HA
  overrides and entity identities.
- `fabman.turn_on` optionally reassigns the resulting usage to `member_id` or
  `email_address`. Leave both empty to retain the API-key member. Existing switches
  and off commands continue to work without member selection.
- Updated README covers current behavior, installation, webhooks and action usage.

## Optional member action

```yaml
action: fabman.turn_on
target:
  entity_id: switch.your_fabman_resource
data:
  email_address: member@example.com
```

Alternatively, supply `member_id: 12345` instead of the email. Both fields together
are rejected. Invalid or ambiguous members fail before activation. The configured
API account still authorizes the activation; selecting another member does not
check that member's training or access rights and can change their charges.

Fabman provides no direct command-to-usage ID reference. Attribution requires a
unique matching usage in the confirmed command's time window. This is not an
atomic guarantee against simultaneous external controls. If attribution fails
after activation, HA reports an error and the resource may already be on. Check
the Fabman activity log; do not repeat activation just to retry attribution.
Pending attribution is not persisted across reloads/restarts. See the README for
the full limitations, including the in-memory door grant timestamp anchor.

## Validation and remaining limits

239 tests pass on each of Home Assistant 2026.10.1 and 2026.10.2, using Python 3.14.
Tests include real HA entity/action routing and local HTTP scenarios for machine
and door member attribution, concurrency, conflicts and timed releases. Lint passes.
A targeted live door release check was performed during b5 development.
Member reassignment, later hardware updates and bridge display behavior have not
been independently validated on live hardware by this agent. Stable publication
does not remove those limits or guarantee compatibility with other HA versions.

See the [activity contract](../activity-contract.md) and README before migrating
production automations, especially automations that require every resource to be off.

## Upgrade

Install **v0.2.0** in HACS and **restart Home Assistant**. If a beta was selected
manually, use Fabman > **Redownload** > **Need a different version?** > `v0.2.0`.
This is a stable release; enabling beta versions is not required.

Existing configuration, switches and legacy status entity identities are retained.
No new settings are required. Upgrades from v0.1.1 also change legacy status
semantics: unknown and unavailable must be handled explicitly in automations.
Users upgrading from b6 receive the same runtime behavior.

For rollback, redownload v0.1.1 and restart HA. Automations depending on the new
entities or `fabman.turn_on` will need to be adjusted because v0.1.1 lacks them.
