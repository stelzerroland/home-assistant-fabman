# v0.3.0b3 - Check-in attendance and per-user attribution

This beta builds on the POS/Nuki support from v0.3.0b1 and the command confirmation timeout from v0.3.0b2. The latest stable release remains v0.2.0.

## Check-in attendance

- Read-only `checkIn` terminals contribute attendance to a shared space-level roster and Check-in activity event.
- The roster is built from Fabman's active-session snapshots and counts each member once per space even if multiple sessions are open.
- New check-in/check-out events identify the affected Fabman member. The initial snapshot establishes a baseline and does not replay old visits.
- Check-in terminals remain read-only: the integration does not expose a control switch or send commands to them.

## Home Assistant user to Fabman member mapping

An administrator can configure an optional mapping for each HA user in **Fabman integration → Configure**. Select the HA user and enter the Fabman member's numeric ID or exact email address. Email is resolved against the integration's Fabman account, and the canonical member ID is stored in that config entry's options. Mappings can be changed or removed later.

For `switch.turn_on` and `fabman.turn_on`, a caller with an HA user ID uses that user's configured mapping. If the HA user has no mapping, the activation stays attributed to the Fabman API-key member; HA does not automatically reassign it. Calls without an HA user context also use the API-key member by default. In `fabman.turn_on`, an explicit member ID or email is supported only for context-free calls; an authenticated HA user's mapping takes precedence.

Each accepted activation creates an **Activation** event on its resource. The event includes the HA actor, attribution path and assignment outcome. The resource status sensor exposes the latest activation as `last_activation_*` attributes. These latest-activation details are kept in memory and reset when the integration reloads or Home Assistant restarts.

Fabman member reassignment uses the usage-log correlation and optimistic locking described in the README. If activation has already been accepted but assignment cannot be confirmed, HA reports an error; inspect the activity log and do not repeat the activation just to retry attribution. The integration does not check the selected member's access rights, training or presence.

## Install or roll back in HACS

Open **HACS → Fabman → ⋮ → Redownload**, enable **Show beta versions**, select **v0.3.0b3**, download and restart Home Assistant.

To return to the previous beta, redownload **v0.3.0b2** and restart. To return to stable, disable beta versions and select **v0.2.0**. Before rolling back, review automations and dashboards that use beta-only attendance, POS, Nuki or Activation entities. Updating or rolling back does not cancel queued Fabman commands.
