# v0.2.0b6 - Optional usage member assignment (beta)

This beta adds `fabman.turn_on` for a controlled live pilot. Normal switch
controls continue to use the member associated with the configured API key.
The additional action accepts either `member_id` or `email_address` to reassign
the resulting usage. Leave both empty to retain the API member. Providing both
is rejected before activation. No HA-user mapping or additional entity is added.

```yaml
action: fabman.turn_on
target:
  entity_id: switch.eingang_office_og
data:
  email_address: member@example.com
```

Replace the example entity and email address with actual values. Alternatively,
use `member_id: 12345` instead of `email_address`. The action is also available
under Developer tools > Actions with a Fabman switch target.

## Behavior and limitations

- Member resolution and account checks happen before activation. An email search
  must return exactly one exact match; use the numeric ID if the search is ambiguous.
- Activation still uses the configured API account's permissions, not the target
  member's training or access rights. Reassignment can affect charges and discounts.
- After activation, the integration waits for command completion and matches one
  new allowed usage by account, resource, original command member and the command's
  creation-to-completion time window. It refuses missing or multiple matches and
  does not reassign a pre-existing running machine usage.
- Fabman supplies no direct command-to-usage ID reference. This is conservative
  correlation, not an atomic attribution guarantee against simultaneous external
  controls. Use a quiet resource for the first live checks.
- The usage is re-read and changed with its current `lockVersion`. An update
  conflict is reported; activation is never retried to retry assignment.
- If assignment cannot be confirmed after activation, HA raises a clear error.
  The resource may already be on, and the usage may still belong to the API member.
  Check the Fabman activity log before taking any further action.
- Local activation commands for one resource are serialized. Explicit off commands
  remain immediate. Assignment state is not persisted across reloads/restarts.
- For an assigned door usage, the original verified grant time is retained in
  memory so editing the member does not extend its release through an updated
  timestamp. After reload/restart, normal API-derived activity rules apply.

The README has also been updated for current entities, lifecycle synchronization,
HACS installation, webhooks, migration behavior and the new action.

## Validation and live pilot

239 tests pass on each of Home Assistant 2026.10.1 and 2026.10.2. Tests include
local HTTP end-to-end assignment for machine and door usage, real HA action
routing, invalid and ambiguous members, unrelated or concurrent usage, update
conflicts, existing switch behavior and door release timing. Python lint passes.
No live activation or modification of real member/usage records was performed
for this release. These tests do not establish live hardware behavior.

For the initial pilot, select one known member and a quiet resource. Check:

1. Normal switch use still attributes usage to the API-key member.
2. The new action accepts an ID or an email and assigns the new usage correctly.
3. A nonexistent member or both selectors produces an error before activation.
4. For a machine, the selected member remains assigned after stopping and later
   bridge updates; check any associated charges.
5. For a door, HA returns to off after its release interval. Do not interpret
   Activity as a physical contact state or assume the bridge display changes.

See the [activity contract](../activity-contract.md) for general migration limits.

## Update

In HACS, open Fabman > **Redownload** > **Need a different version?** > `v0.2.0b6`
(enable beta/prerelease versions if needed), download, then **restart HA**.
Existing configuration and entity identities are preserved. No new configuration
is needed to retain existing behavior. Stable-only installations remain on v0.1.1.
